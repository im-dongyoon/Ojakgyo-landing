# 0001. 웨이팅리스트와 유입 집계

## 결정

### 무엇을 받나

- 모달 폼에서 **이름 · 휴대폰 번호**를 받는다. 개인정보 수집 · 이용 동의 체크가 없으면 저장하지 않는다.
- 휴대폰 번호는 숫자만 남겨 `01012345678` 꼴로 저장한다. `+82`로 시작하면 `0`으로 바꾼다. 같은 번호는 한 번만 저장한다.
- 이미 신청한 번호도 **완료로 응답**한다.
- 봇 차단은 우선 사람에게 안 보이는 입력칸(honeypot) 하나로 한다. 채워져 오면 저장하지 않고 완료로 응답한다.

### 유입은 어떻게 보나

- 별도 분석 도구는 붙이지 않는다. 방문과 신청을 DB에 직접 남기고 **DB 뷰로 집계**한다.
- 페이지를 열면 `visits`에 한 줄을 남긴다. 신청하면 `waitlist` 행에도 같은 유입 정보를 남긴다.
- 유입 경로(`source`)는 이 순서로 정한다.
  1. 주소에 `utm_source`가 있으면 그 값 (`utm_medium`, `utm_campaign`도 같이 저장)
  2. 없으면 이전 페이지(referrer)의 도메인. `www.` · `m.` · `l.` 같은 앞부분은 뗀다 (`l.instagram.com` → `instagram.com`)
  3. 둘 다 없거나 우리 사이트 안에서 온 경우 `direct`
- 같은 사람의 재방문을 묶으려고 무작위 방문자 ID를 쿠키(`oj_vid`, 1년)에 둔다. 이름 · 번호와는 신청할 때만 연결된다.
- 집계 뷰
  - `inflow_by_source`: 경로별 방문 수 · 방문자 수 · 신청 수 · 전환율
  - `inflow_daily`: 날짜(한국 시간)별 · 경로별 같은 숫자

### 권한

- 서버만 **secret 키**로 쓴다. 브라우저에는 Supabase 키가 나가지 않는다.
- 모든 테이블 · 뷰에서 `anon` · `authenticated` 권한을 걷어 낸다. 행 단위 보안은 켜 두고 정책은 만들지 않는다. 그래서 공개 API로는 아무것도 읽거나 쓸 수 없다.
- 집계와 신청 목록은 Supabase 대시보드에서 본다.

## 이유

- 처음에는 publishable 키 + "새 행 넣기만 허용"으로 설계했다. 그런데 방문 기록까지 공개 키로 열면 누구나 API를 직접 불러 방문 수를 부풀릴 수 있다. 전화번호 같은 개인정보도 다루게 됐으니, 쓰기 경로를 서버 하나로 모으고 공개 API는 완전히 닫았다.
- 중복 번호를 오류로 알려 주면 "이 번호가 신청돼 있는지"를 밖에서 확인할 수 있다.
- 유입 정보를 신청 행에도 따로 남기는 이유: 쿠키가 막혀 방문 기록이 없더라도 신청의 유입 경로는 남게 하려고.
- 방문 수는 새로고침마다 늘어난다. 그래서 방문자 수(고유 방문자 ID 수)를 같이 보고, 전환율은 방문자 수 기준으로 계산한다.

## 나중에 볼 것

- 트래픽이 붙으면 요청 횟수 제한(Vercel Firewall 등)을 추가한다.
- 개인정보 처리방침과 동의 문구(수집 항목 · 목적 · 보유 기간)는 화면 작업 때 넣는다.
- 출시 후 신청 데이터를 언제 지울지 보유 기간을 정한다.
